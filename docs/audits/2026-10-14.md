# Project audit, October 14, 2026

The audit reviewed the complete tracked project at
`80baf84c8f9316a500cc280fd784abf901f34eff`. Independent agents reviewed the
backend, frontend, and tooling. Fresh correctness and comment reviews checked

## Confirmed defect and correction

A successful Spotify token response could contain a nonempty access token
that native HTTP headers reject. The handler cached that token before the
playback request constructed its Authorization header. CRLF, NUL, and
non-ByteString token values each produced two consecutive HTTP 500 responses
with one refresh request and no playback request. The synthetic reproduction
recovered only after advancing beyond the 59-minute token cache lifetime.

The handler now validates the full bearer-token grammar before updating shared
state. The guard follows
[RFC 6750 section 2.1](https://www.rfc-editor.org/rfc/rfc6750.html#section-2.1).
It preserves legal punctuation and trailing padding without changing tokens.
The existing private error response, expiry policy, shared refresh, and
identity-safe 401 recovery stay in their canonical handler.

The regression cases use native Request construction inside the fetch mock.
They cover 26 malformed token values and three valid punctuation/padding
forms. Nineteen new malformed-string cases failed against the original code.
After the fix, all 92 API tests passed. Direct probes changed from repeated
500 responses to a private 500 followed by successful 200 responses on the
next two requests. Valid tokens reuse the cache and reach playback unchanged.
